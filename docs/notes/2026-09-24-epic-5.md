# Epic 5: the postings feed

## What the pattern was

One interface (`crawl.Fetcher`) implemented six times, one manifest and one status file per
board, and a tree tripwire (`internal/crawl/tree_test.go`) that decodes every document under
`postings/`, `status/` and `runs/` with `DisallowUnknownFields` before the workflow is allowed to
commit. Two live runs into a scratch directory proved the pipeline end to end: run one wrote 693
postings across all six fetchers (`greenhouse/gitlab` 207, `lever/palantir` 319, `ashby/linear`
30, `workable/huggingface` 8, `remoteok/all` 99, `rendered/linear-careers` 30); run two, seconds
later against the same live boards, wrote 0 — nothing changed, so `git log` on any one posting
stays that posting's real history rather than gaining a commit every six hours. The tripwire then
ran against the 693 real documents copied in from that run and passed; the copy was removed before
committing, leaving `postings/`, `status/` and `runs/` absent from every commit except the ones the
Action itself makes.

## What surprised me

The rendered path and the API agreed exactly: Ashby's static HTML for `jobs.ashbyhq.com/linear`
holds no role anchors, but Rod found 30 and `ashby/linear`'s own API also reports 30 — the same
board, two fetch paths, one number. Also, the fixtures under `internal/fixtures/` are tiny
recorded samples (1-2 postings per board, used for `-dry-run` and CI) and gave no sense of scale;
the live boards are two to three orders of magnitude larger, and `lever/palantir` at 319 was the
single biggest surprise — nothing in the fixture or the spec suggested one board would dwarf the
rest. No board did anything the fixtures failed to predict in shape: every live response decoded
the same way its fixture did, no unexpected fields, no board reporting an error or a moved slug.

## What I would do differently

Nothing about the crawl pipeline itself — a live run against six real boards produced no
surprises in structure, only in scale. If starting over, I would size the fixtures nearer to a
realistic board (tens, not a couple, of postings) so the dry run's `changes` counts read more like
a real crawl's, rather than discovering the gap only by running live.

## What I still do not understand

Q1 stays the one unverified assumption in the epic: whether a scheduled workflow that commits
every six hours is enough to keep GitHub from treating the repository as idle and disabling the
schedule. The ruling's fallback (atlas's staleness check plus `gh workflow enable crawl.yml`) is
written and ready, but nothing here proves the schedule survives sixty idle days, because
verifying that takes sixty idle days — this epic does not run that long.
